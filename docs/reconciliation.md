# Сверка неопределённых отправок

Случаи `FAILED / RECONCILIATION_REQUIRED` видны на странице заявок и в
карточке конкретной заявки. Случай остаётся открытым, пока нет сохранённого
подтверждения результата. Принятая шлюзом заявка при этом не удаляется.

## Порядок работы

Worker автоматически сверяет подтверждённые случаи при запуске и каждые пять
секунд, пакетами до 20 событий. Сверка работает отдельно от отправки заявок,
с таймаутом две секунды. Если получено допустимое FIX-подтверждение, случай
закрывается с оператором `system:fix-reconciliation` и ссылкой на доказательство.
Перезапуск или несколько экземпляров gateway не создают повторные решения:
условия перепроверяются под блокировками в транзакции. Ошибка записи оставляет
случай для следующей сверки и отражается в журнале worker.

1. Открыть заявку и проверить FIX ClOrdID, адаптер, QUIK OrderID, исполнения
   и историю событий. Сверять именно идентификаторы заявки, а не только цену
   или инструмент в стакане.
2. Дождаться подтверждения торгового контура. Для отправки подходит применённый
   `ORDER_EXECUTION_REPORT` со статусом ACKNOWLEDGED, PARTIALLY_FILLED, FILLED,
   CANCELLED, REJECTED или EXPIRED, сохранённый не раньше создания queue event.
   Для отмены подходит только конечный статус FILLED, CANCELLED, REJECTED или
   EXPIRED: первоначальное подтверждение заявки не подтверждает результат отмены.
3. Если автоматическая сверка ещё не закрыла случай, оператор, ADMIN или SUPER_ADMIN вводит комментарий и закрывает случай
   по подтверждению. История хранит оператора, время, комментарий, исходную
   ошибку и ID подтверждающего события. Запись истории и перевод outbox в DONE
   выполняются одной транзакцией. Конкурирующий запрос получает 409.

Закрытие не меняет заявку, исполнения или `fix_send_attempted_at`, не повторяет
отправку и не возвращает событие в PENDING. Отсутствие заявки в стакане не
считается доказательством, что она не была принята.

## API

- `GET /api/v1/admin/reconciliation?limit=100&order_id=<uuid>` — открытые случаи
  и история; order_id необязателен, limit от 1 до 500. Открытые случаи идут первыми.
- `POST /api/v1/admin/reconciliation/<event_id>/resolve` с `{"note":"..."}` —
  закрыть по подтверждению; 409 при отсутствии доказательства или закрытом случае.

Требуется миграция 000024. История хранится в `outbox_reconciliations`.

## Следующие этапы

Автоматический запрос статуса через FIX требует подтверждения поддержки и
семантики OrderStatusRequest у ARQA. Текущий QUIK API стакана этого не заменяет.
Импорт внешнего подтверждения и разбор cancel reject пока не реализованы:
неподтверждённые случаи остаются открытыми. Произвольное ручное выставление
торгового статуса не предусмотрено.

Интеграционные проверки выполняются только на одноразовой БД:
`go test -race -tags integration ./internal/outbox -run TestReconciliation`.
Проверяются отсутствие доказательства, устаревшее/игнорированное событие,
ACK вместо результата отмены, конкурентное закрытие, сохранность send fence
и откат закрытия при ошибке записи истории.
