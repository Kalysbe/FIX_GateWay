# Сделки и исполнения заявок

## Решение и результат пересмотра 19.10.2026

Требование пользователя: хранить номер сделки QUIK и обе реальные стороны в БД, восстановить пропуски и контролировать дальнейшую полноту. Строки контрагента, построенные интерфейсом из одного отчёта, удалены. Источник восстановления — явно разрешённое пользователем чтение `http://192.168.0.89:5000/api/trades`. Исходники, настройки и контейнеры других проектов не исследовались.

Сверка сохранённого снимка QUIK с исходной БД:

| Показатель | Значение |
|---|---:|
| Сделок в QUIK | 11 167 |
| Реальных сторон в QUIK | 22 334 |
| Ранее представлено в executions | 21 164 |
| Сделок с одной сохранённой стороной | 1 032 |
| Сделок, отсутствовавших целиком | 69 |
| Восстановлено реальных сторон в новом реестре | 1 170 |

Количества, цены и номера заявок у всех 21 164 старых исполнений совпали с QUIK. На копии исходной БД после переноса — 11 167 сделок, 22 334 стороны, 0 неполных сделок и 0 ошибок исходных отчётов. Повторный импорт не изменил количества. Старые исполнения и финансовые итоги заявок не пересчитываются.

## Причины пропусков

Дополнительное расследование 19.10.2026 различает доказанную ошибку обработки и отсутствие исторических свидетельств. Ранее сделанный вывод «адаптер не прислал отчёты» не доказан: отсутствие записи в БД не подтверждает отсутствие сообщения на входе Gateway.

### Пять подтверждённых пропусков при дедупликации

Отчёты BUY по сделкам №573–577 от 02.10.2026 сохранены в `order_events`, но отсутствовали в `executions`. ExecID `LIST_GBA-9F-B-1-1-N` — `LIST_GBA-9J-B-1-1-N` совпали с исполнениями от 04.09.2026. В старой реализации (`b482b02`, `backend/internal/orders/store.go`, `ApplyExecutionReport`) проверка `SELECT EXISTS ... WHERE exec_id=$1` выполнялась без даты и заявки; при совпадении вставка просто пропускалась. Схема также содержала глобальный `UNIQUE(exec_id)`. Здесь получение отчётов Gateway и неправильное исключение новых исполнений подтверждены сохранёнными данными и кодом. Ограничение заменено миграцией 26; эти пять сторон восстановлены из исходных отчётов в новом реестре.

### Отчёты без найденной локальной заявки

Прежняя модель `executions.order_id NOT NULL` хранила только исполнения локальных заявок. В сохранённой истории QUIK есть 1 165 сторон, для которых сейчас нет ни локальной заявки Gateway, ни сохранённого исходного FIX-отчёта.

В версии `b482b02` обработчик `ApplyExecutionReport` сначала вызывал `lockOrderForFIX`. Если заявка не найдена, он возвращал ошибку **до** записи `order_events` с исходным FIX. `Server.OnExecution` записывал ошибку в лог и завершался, не возвращая её в FIX callback для повторной обработки. Таким образом, даже полученный отчёт мог не оставить исходного сообщения в БД. Это доказанный дефект старой обработки, но не доказательство прохождения каждого из 1 165 отчётов именно этим путём.

Транспорт использовал `quickfix.NewNullLogFactory()`; отдельного полного журнала принятых FIX-сообщений не было. Событие наблюдаемости `FIX_EXECUTION_REPORT` сохраняло ClOrdID, но не номер сделки и полное тело сообщения. Поэтому по имеющимся локальным данным нельзя для каждой отсутствовавшей стороны однозначно отличить неотправленный адаптером отчёт от отчёта, отвергнутого Gateway до сохранения.

### Границы истории и недостаток контроля полноты

Из 1 170 добавленных сторон 132 относятся к 66 сделкам от 19.08.2026 — раньше первой сделки в старом `executions` (04.09.2026). Их отсутствие само по себе не доказывает потерю при приёме: снимок QUIK охватывает более раннюю историю. Оставшиеся 1 038 сторон относятся к датам, представленным в старой БД: пять имеют подтверждённую ошибку дедупликации, для 1 033 точка исторического пропуска пока не установлена. Из 69 полностью отсутствовавших сделок 66 относятся к августу, одна — к 05.10, две — к 08.10.

До пересмотра не было автоматической сверки полного списка сделок и обеих сторон с QUIK. Поэтому корректная обработка части локальных заявок и успешная FIX-сессия не обеспечивали проверку полноты. Восстановление и новые проверки не закрывают историческое расследование. Для оставшихся случаев нужны исходящие журналы ARQA и фактические настройки соответствующих FIX-сессий за нужные даты; их чтение за пределами текущего проекта требует отдельного разрешения пользователя по `AGENTS.md`.

## Новая структура

| Таблица | Назначение |
|---|---|
| `public.trades` | Одна биржевая сделка: `quik_trade_num`, полный `trade_match_id`, дата, инструмент, класс, количество и цена |
| `public.trade_sides` | Реальная покупка или продажа; номер заявки QUIK, фирма, клиент, счёт; необязательные связи с локальной заявкой и исполнением |
| `public.trade_reports` | Неизменяемый исходный FIX-отчёт либо запись истории QUIK; источник, хеш, состояние обработки и ошибка |
| `public.trade_side_reports` | Связь стороны с подтверждающими исходными записями |
| `public.trade_sync_runs` | Время, источник, количество и результат автоматической сверки |
| `public.executions` | Исполнения локальных заявок для существующего брокерского API и расчётов заявок |

Уникальность сделки: полный номер, дата, инструмент и класс. Уникальность стороны: сделка + BUY/SELL. Номера сохраняются строками без преобразования в float. Заявки, ExecID и недоступные данные не генерируются. Для истории QUIK `quik_order_num` хранится непосредственно; полный OrderID подставляется только из настоящего FIX-отчёта или подтверждённой локальной заявки. Неизвестное время не заменяется выдуманным временем исполнения.

## Сохранение и восстановление

Входящий FIX-отчёт сначала сохраняется в `trade_reports`, независимо от локальной заявки. Запись сделки/стороны и связь с источником коммитятся вместе. При отказе БД входящий durable inbox сохраняет сообщение и повторяет обработку. Конфликт количества, цены, стороны или заявки оставляет исходную запись со статусом ERROR и не переписывает подтверждённые данные.

При `TRADE_RECONCILIATION_ENABLED=true` выполняется перенос ранее сохранённых FIX-отчётов при запуске и сверка истории QUIK при запуске и каждую минуту. Origin читается из текущей настройки `quik_api_base_url`. Доступ только на чтение; не выполняются торговые операции в QUIK. Обрыв JSON, ошибка HTTP, неполная пара и конфликт источников не считаются успешной сверкой. Повторный запуск дополняет данные без дублей. Недоступность источника видна в последнем результате сверки; она не скрывается статусом полной загрузки.

### Дополнительная защита от новых пропусков

Транспортный журнал `backend/internal/fixaudit` подключён к QuickFIX вместо `NewNullLogFactory`. Входящее сообщение сохраняется и синхронизируется с диском до разбора/валидации QuickFIX и вызова бизнес-обработчика. Сохраняются входящие и исходящие сообщения, события сессии, UTC-время, сессия, направление, MsgSeqNum, MsgType и SHA-256 исходных байтов. `raw_base64` сохраняет исходные байты, в том числе невалидный UTF-8. Пароли и RawData не сохраняются открытым текстом; для таких записей выставляется `credentials_redacted`, хеш относится к оригиналу. Транспортный журнал не заменяет durable inbox и `trade_reports`.

Файлы находятся в `<FIX_SESSION_DIR>/<adapter-id>/audit/*.audit.jsonl` на постоянном томе FIX. Ротация выполняется по UTC-дню и при достижении 64 MiB; автоматического удаления доказательств нет. `FIX_AUDIT_MAX_BYTES` задаёт общий лимит сохранённых сегментов на адаптер, по умолчанию 4 GiB. При 70% появляется тревога. Ошибка записи/синхронизации или исчерпание лимита останавливает процесс; он не продолжает обработку незаписанного сообщения. При запуске проверяются доступность записи, лимит и отсутствие оборванного последнего ряда каждого сегмента. Оборванный файл сохраняется для разбора, соединение не открывается.

Сверка QUIK проверяет идентификаторы всех сторон, ранее реально наблюдавшихся в этом источнике. Пустой массив, исчезнувшая целая пара, замена старой пары новой при неизменном числе строк и сокращение охвата дат считаются ошибкой. Полученные реальные данные сохраняются, прежняя история не удаляется. Даже при ошибке остаются время и результат попытки; отметка последней успешной сверки не обновляется. Источник сейчас имеет контракт полной истории `/api/trades`; переход на источник с окном дат требует отдельного изменения этого контракта, а не отключения проверки.

Проверка состояния выполняется каждые 15 секунд. Уведомления сохраняются существующим механизмом Gateway и доступны в его интерфейсе:

| Условие | Тревога |
|---|---|
| Более двух минут нет обеих сохранённых сторон | `TRADE_PAIR_INCOMPLETE` |
| В исходных записях есть ошибки или конфликт | `TRADE_SOURCE_ERROR` |
| Последняя завершённая сверка неуспешна | `TRADE_SYNC_FAILED` |
| Нет успешной полной сверки более пяти минут | `TRADE_SYNC_STALE` |
| Нельзя проверить состояние БД | `TRADE_MONITOR_UNAVAILABLE` |
| Входящая очередь неисправна или задержана более 30 секунд | `EXECUTION_INBOX_BLOCKED` |
| Журнал адаптера заполнен на 70% | `FIX_AUDIT_CAPACITY_<adapter-id>` |
| В реальном ARQA-подключении включён ResetOnLogon | `FIX_SEQUENCE_RESET_<adapter-id>` |

Тревога появляется при возникновении, повторяется не чаще раза в пять минут и имеет отдельное уведомление о восстановлении. Отказ запуска адаптера также формирует уведомление. При недоступности БД её уведомление сохраняется после восстановления, если проблема ещё актуальна; независимые метрики показывают отказ проверки. Новые внешние получатели уведомлений не настроены. Метрики и правила Prometheus доступны для операторского контроля.

Страница сделок показывает время последней **успешной** сверки, отдельно предупреждает об устаревшей проверке. Полные пары в БД сами по себе не означают актуальную полноту QUIK. Механизм обнаруживает отсутствие данных в наблюдаемой истории; отсутствие сделки одновременно во всех доступных источниках можно проверить только независимой выгрузкой со стороны площадки.

Новые резервные копии вне рабочего диска не добавлялись по прямому указанию пользователя. Журнал FIX сохраняется на текущем постоянном томе; это доказательства приёма, а не независимая резервная копия.

При проверке 19.10.2026 у `quik-fix-1` и `quik-fix-2` установлено `reset_on_logon=true`. Настройки не менялись: переход на непрерывную последовательность требует согласования с сервером ARQA и проверки resend. До этой проверки нельзя считать восстановление отчётов средствами одной FIX-сессии достаточной защитой; журнал и независимая сверка QUIK необходимы. Симуляторные сессии этим предупреждением не охватываются.

Страница сделок использует реальные записи `trades/trade_sides`, показывает покупку и продажу рядом, номер QUIK и источники FIX/QUIK. В таблице — последние 500 сделок целиком с обеими сохранёнными сторонами; глобальная полнота и последняя сверка показаны отдельно. Карточка и печать используют те же сохранённые данные, доступ к исторической карточке не ограничен этим окном.

Брокерские endpoints и события остаются ограничены своим брокером и локальными исполнениями. История других сторон доступна только административному API.

## Миграция и проверка

Миграция 30 добавляет новые таблицы. Миграция 31 создаёт индекс существующих заявок CONCURRENTLY. Данные переносятся отдельным действием, без UPDATE количества, цены, статуса и итогов старых заявок/исполнений. Резервная копия исходной БД и снимок QUIK находятся в игнорируемом Git каталоге `artifacts/trade-ledger`.

Команда для воспроизводимого переноса в выбранную БД: `trade-reconcile -migrate -quik-file <сохранённый ответ API>`. DSN берётся из `DATABASE_URL`. Это команда записи в БД Gateway; применять только к явно выбранной БД. Повторная проверка импорта: `-backfill=false -quik-file ...`. Для рабочего gateway перенос выполняется автоматически до первой сверки при включённом параметре.

Откат приложения сохраняет новые таблицы и исходные отчёты. Down миграции 30 отказывается удалять заполненный реестр; исправление схемы выполняется следующей прямой миграцией. Восстановление резервной копии поверх новых данных требует отдельного решения с учётом поздних исполнений.

Проверки усиления: реальное исчерпание выделенного tmpfs 64 KiB; невозможность продолжить после ошибки записи; сохранность входящих/исходящих байтов и скрытие паролей; отказ при усечённой истории и подмене пары при том же числе строк; уведомление о недоступном QUIK; отключение PostgreSQL на 35 секунд и SIGKILL Gateway на отдельном симуляторном стенде; повторный запуск без дублей; Go race detector. В тестовом симуляторе добавлены номера сделки/заявки, дата и класс, чтобы проверять тот же реестр, что и на ARQA.

Проверки исходного переноса: обработка FIX без локальной заявки, загрузка реальной противоположной стороны из QUIK, числовая точность, отсутствие выдуманной стороны, идемпотентность, конфликты, усечённая история, API карточки, область доступа, сохранность старых исполнений. Полный перенос и повторный импорт проверены на отдельной БД, восстановленной из резервной копии проекта.
